## The problem

ML-based vibration fault diagnostics are accurate but opaque. An analyst cannot tell a maintenance lead **why** a particular fault was flagged, which is a non-starter for safety-critical rotating equipment where a wrong call has consequences. The brief was the opposite of an ML approach: build a transparent rule-based diagnostic engine that ranks probable mechanical, bearing, and electrical faults with traceable for/against evidence, aligns severity to ISO 10816, and lets new rules be added without retraining anything.

## Constraints

- **Explainable verdicts**: every fault rank ships with an evidence chain (which features matched, which did not).
- **Cover the major fault families**: mechanical (unbalance, misalignment, looseness), bearing (BPFO, BPFI, BSF defects), electrical (rotor bar, stator eccentricity), spectrogram-based transients.
- **ISO 10816 alignment**: severity needs to map onto the standard zones (A through D) so customers can compare verdicts to their existing thresholds.
- **Extensible without retraining**: adding a new fault rule should be code, not data work.

## Approach

**Feature extraction.** 30+ features computed per measurement window: FFT amplitude / phase, Hilbert envelope (the classic envelope-detection trick for bearing defects), crest factor, kurtosis, harmonic and sideband detection, and STFT-derived transient indicators. Each feature has a defined contract (input shape, output range, expected sensitivity to which fault families) so rules can rely on them.

**Bearing-defect frequencies.** Computed from bearing geometry (number of balls, ball diameter, pitch diameter, contact angle, running speed) using the standard formulas. 12 SKF profiles bundled out of the box; analysts can register custom geometries. The defect frequencies (BPFO outer race, BPFI inner race, BSF ball spin, FTF cage) become the search targets in the spectrum for the bearing rules.

**Rule engine.** 13 rules cover the major fault families. Each rule is a function from (features, frequencies, machine context) to a structured verdict: probable fault, confidence score, severity class, and an evidence chain listing the features that contributed for and against. The rules are independent; new ones plug in without touching the others. There is no global model to retrain.

**ISO 10816 mapping.** Overall vibration velocity (RMS over a defined frequency band) maps onto the four ISO zones (A good, B acceptable, C marginal, D unacceptable) per machine class. The severity result lives alongside the rule verdicts so the same screen tells you both "what is wrong" and "how bad is it overall."

**Surfaces.** A PyQt5 6-tab workflow for analysts who want to load a CSV and explore. A headless Python API for integration into condition-monitoring pipelines. Both call the same rule engine.

## What broke

Bearing-defect rules over-fired on machines with running speeds close to bearing-geometry frequencies. The defect-freq peak and the running-speed peak overlapped in the spectrum, so the rule kept seeing "evidence" of a bearing fault that was really just normal operation. Added a frequency-margin check that suppresses the bearing rule when defect frequencies fall within ±2% of the running-speed harmonic. False positives dropped to acceptable levels without losing real detections.

## What I would do differently

Bake severity-zone calibration into every rule from the start. Computing severity separately is convenient but it splits "what is wrong" from "how worried should I be" across two code paths. Severity belongs in the rule's own output tuple, alongside the confidence and evidence chain.
