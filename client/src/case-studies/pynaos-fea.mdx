## The problem

Off-the-shelf FEA packages for offshore structures are expensive, closed-source, and slow to iterate against. If you want to script a new analysis driver, embed FEA inside another tool, or even just check what a commercial solver actually computed, you cannot. The brief was to build a self-contained Python FEA engine that covers the analysis types offshore work actually needs (static, dynamic, eigenvalue, buckling, including non-linear variants), pairs them with offshore-specific physics (wave loading, geotechnical p-y curves, P-Δ effects), and ships with a desktop workstation that an analyst can drive without writing Python.

## Constraints

- **Pure Python**: no compiled FEM dependency, no native solver linkage. Portability and embeddability come first.
- **Six analysis drivers minimum**: linear and non-linear static, eigenvalue, linear and non-linear dynamic, buckling. Each must share the same element library.
- **Offshore physics is non-negotiable**: Airy, Stokes, and Chakrabarti wave kinematics; Morison forces; API RP 2A p-y and t-z geotechnical curves; P-Δ effects.
- **Reproducibility**: results must be reproducible across cold installs. Reference scenarios committed alongside expected outputs.
- **Usable by analysts who do not script**: a desktop GUI is not optional.

## Approach

**Skyline storage + LDLᵀ.** Offshore-structure connectivity is sparse but banded (jacket members tie back to a small number of nodes). Skyline storage matches that pattern: only the active band per column is stored, factorisation works in place, and triangular solves are just descents through the band. For the typical 3D Timoshenko beam meshes I was targeting it beat dense storage by an order of magnitude on memory and gave a useful constant-factor win on factor + back-substitute time.

**Lanczos for eigenvalues.** First n modes are what offshore work actually needs (modal analysis for fatigue spectra, mass participation, buckling factors). Full factorisation is wasted work. Lanczos converges to the lowest-magnitude eigenvalues quickly, with a re-orthogonalisation pass to keep numerical drift from contaminating the basis.

**Hydrodynamics module.** Airy works for linear shallow-water cases, Stokes 5th order extends into steeper non-linear waves, Chakrabarti for current-coupled regimes. Morison gives the force on slender members from the wave kinematics. The same wave-kinematics output drives both static-equivalent and time-domain dynamic loading paths.

**Geotechnical foundations.** API RP 2A p-y and t-z curves wrap the soil-pile interaction. Depth-of-fixity gets computed from the p-y curve so the bottom of the structural model can be a clean fixed boundary at a realistic depth instead of dragging soil non-linearity through the whole solve.

**Desktop workstation.** PyQt5 + OpenGL viewer over the Python core. Seven analysis workspaces (one per driver, plus model setup), validation and readiness checks before a run, command palette for power users, auto-save so an analyst never loses a half-set-up case.

## What broke

An early non-linear dynamic release silently used the small-strain assumption inside the P-Δ branch, which gave plausible-looking but slightly under-conservative top-of-jacket displacements. Caught it because a reference scenario flagged a regression at the 4th decimal place between releases. The fix was small. The real lesson was that reference scenarios committed to git **with their expected outputs** are the cheapest insurance you can buy on a numerics codebase. Inputs alone do not catch this class of bug.

## What I would do differently

Start with the hydrodynamics module instead of the structural core. The structural core could have been bootstrapped from existing primitives in any number of libraries; the hydrodynamics + geotechnical layer is what makes this engine actually useful for offshore work, and getting that right earlier would have surfaced API decisions in the rest of the stack sooner.
