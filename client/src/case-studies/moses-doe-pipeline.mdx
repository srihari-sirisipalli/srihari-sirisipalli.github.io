## The problem

Bentley MOSES is the offshore-engineering standard for sea-transport hydrodynamics, but it's a single-case GUI tool. To explore design space at any meaningful resolution you need to drive it programmatically across thousands of parameter combinations, parse its multi-format outputs, and feed the results into something that lets you ask new questions without re-running the simulator. None of that is built in.

The brief was: characterise stability and motions for a large barge across a wide ballast envelope, then train surrogate models so engineers can iterate at design time instead of waiting for the next simulation queue.

## Constraints

- **MOSES is licensed**: every case spends a license-second. The pipeline must skip already-completed work after any restart and never accidentally re-run.
- **Outputs are text + Excel + binary**: you can't just pickle them. The parser has to be defensive against MOSES warning lines, layout changes, and partial completions.
- **The DOE has to actually cover** the operational envelope. Naive uniform sampling misclusters. Stratification matters.
- **15,000 cases × dozens of derived quantities** is enough that orchestration and storage need to be deliberate, not improvised.

## Approach

**Sampling.** Uniform Latin Hypercube over 80 inputs leaves the operational corners under-sampled because MOSES outcomes are non-linear in ballast distribution. The fix was 4-zone stratification (Light / Medium / Heavy / Mixed) with per-zone LHS, then concatenation and shuffling. The same code path generates train/test splits at sample time so downstream surrogate training is leakage-controlled.

**Orchestration.** Each case writes a marker file when it finishes parsing. Restarting the orchestrator skips any case whose marker exists. That single primitive cost an afternoon to implement and saved every subsequent re-run.

**Parsing.** Per-case output landed as one 12-sheet `.xlsx` workbook covering 6-DOF motions and accelerations at flotation and motion points, longitudinal bending moment / shear force, intact and damage stability across 28 compartments, and weight distribution. The parser is paranoid by design: bad cases are quarantined, never silently dropped.

**Surrogates.** Two heads were trained: a stability classifier (passes IMO criteria yes/no) and a motion regressor (peak-period responses). XGBoost and LightGBM as the workhorses; a small PyTorch MLP for the motion targets where smoothness mattered. SHAP for feature attribution.

**Optimisation.** Optuna for single-objective ballast tuning, PyMoo NSGA-II for the multi-objective stability-vs-motion frontier. Both run on top of the surrogate, not the simulator, so design iterations cost milliseconds instead of minutes.

## What broke

The first parser was naive about MOSES warning lines. Three of them shifted column offsets in a way that silently produced offset bending-moment values for ~40 cases. Caught it during sensitivity analysis when SHAP flagged a feature whose physical relationship made no sense. Lesson: parser tests using known-good reference cases should run *before* a long DOE batch, not after. The parser now re-validates against six reference checksums on every cold start.

## What I'd do differently

Push more of the DOE-side metadata (zone, seed, generation timestamp) directly into the case marker file instead of recomputing from the case index. Ten minutes of work that would have made a couple of post-hoc analyses much cleaner.
